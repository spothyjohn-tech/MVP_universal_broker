# Highload 1C-to-DB Batch Broker (Write-Service MVP)

Высокопроизводительное ядро интеграции 1С/ERP систем с OLAP-аналитикой на Go. Архитектурное решение для обработки сверхплотных потоков бизнес-транзакций (Продажи и Остатки), снижающее затраты на серверную инфраструктуру в 10 раз за счёт ультра-оптимального батчинга.

---

## Стек технологий
* **Language:** Go 1.25.1
* **Message Broker:** RabbitMQ (протокол AMQP 0.9.1)
* **Databases:** PostgreSQL (pgx/v5 пул), ClickHouse (Native Driver v2)
* **Config Loader:** Cleanenv (Чтение из `.env` и `YAML`)

---

Сервис предназначен для сквозной потоковой обработки транзакционных логов и оперативного учета остатков, поступающих из систем **1С:Предприятие** через брокер сообщений **RabbitMQ**. Запись осуществляется параллельно в **ClickHouse** (аналитическое хранилище) и **PostgreSQL** (оперативный баланс).

---

## Результаты нагрузочного бенчмарка

Сервис спроектирован для работы с высокой нагрузкой (Highload). Для достижения максимальной пропускной способности используются `sync.Pool` (zero-allocation pipeline), SIMD-оптимизированный парсинг JSON (`bytedance/sonic`) и пакетная вставка (Batch Insert).

Интеграционный тест с физической записью агрегированных данных в **PostgreSQL** (UPSERT) и лога изменений в **ClickHouse** (Append-Only) демонстрирует следующие показатели:

| Метрика | Значение |
| :--- | :--- |
| **Реальная скорость** | `~68 650 записей/сек` |
| **Чистое время записи** | `1.45 сек` |
| **Объем батча** | `100 000 записей` |
| **Записано в PostgreSQL** | `20 662 строк` (схлопывание дублей) |
| **Записано в ClickHouse** | `100 000 строк` (полный лог) |

*Тест проводился на локальной машине с использованием стандартных Docker-контейнеров для БД. Запустить интеграционный бенчмарк можно командой:*
`go test -v -run Test_Usecase_RealDatabase_Throughput ./internal/usecase`

## Архитектура и Дизайн проекта

Проект строго следует правилам **Clean Architecture** (Чистой архитектуры). Направление зависимостей идет извне внутрь: внешние базы данных и транспорт ничего не знают о бизнес-логике, а бизнес-логика (Usecases) зависит только от абстракций (Interfaces).

### Структура каталогов
* `cmd/broker/main.go` — Точка входа. Отвечает за инициализацию конфигурации, пулов соединений и обеспечение плавного завершения работы (**Graceful Shutdown**).
* `internal/domain/` — Ядро системы. Содержит структуры данных (`models.go`), интерфейсы взаимодействия (`interfaces.go`) и конфигурационные контракты. Не имеет внешних зависимостей.
* `internal/usecase/` — Слой бизнес-логики. Управляет сценарием оркестрации (`batch_processor.go`): запрашивает пачку данных у брокера, распределяет её по хранилищам и инициирует подтверждение приема.
* `internal/infrastructure/` — Слой адаптеров. Реализация работы с низкоуровневыми драйверами (ClickHouse, Postgres, RabbitMQ).

## Как это работает (Фундаментальные принципы Highload)

Текущий MVP переведен на **событийно-ориентированную Push-модель (Write-Only пайплайн)**:

### 1. Накопительный Батчинг на приеме (RabbitMQ QoS)
Вместо вычитки сообщений по одному, инфраструктурный адаптер `ConsumeBatch` использует окно ожидания. Сообщения накапливаются в памяти Go до тех пор, пока не наберется лимит количества строк (`cfg.Batch.Size`) или не истечет таймаут ожидания пачки в миллисекундах (`cfg.Batch.Timeout`). UseCase получает на вход уже готовый к вставке строго типизированный пакет структур `BatchData`.

### 2. Ручное пакетное подтверждение (Manual Batch Ack)
В системе реализована строгая гарантия доставки **At-Least-Once**:
* Когда RabbitMQ отдает пачку сообщений в Go, они остаются в брокере в статусе `Unacknowledged`. 
* Если в процессе записи воркер упадет, RabbitMQ мгновенно вернет сообщения в очередь — данные из 1С никогда не потеряются.
* Удаление данных из брокера происходит строго в самом конце метода UseCase. Функция `AcknowledgeBatch` выполняет **Batch Ack** — она берет `DeliveryTag` самого последнего сообщения в пачке и подтверждает его с флагом `multiple = true`, заставляя RabbitMQ удалить всю пачку разом и экономя сетевые пакеты.

### 3. Бинарный стриминг и защита временных меток (Идемпотентность)
* **В ClickHouse Repository** вставка идет через нативный клиент `PrepareBatch` и `Send()`. Данные улетают спрессованным бинарным блоком напрямую в таблицы `sales` и `stocks` движка `MergeTree`.
* **В PostgreSQL Repository** Данные из массивов разворачиваются через unnest() и атомарно сливаются с основной таблицей stock_tables. Поля product_id и warehouse_id выступают уникальным ключом: при конфликте (ON CONFLICT) остатки суммируются, а дата обновления актуализируется.
* **Контроль хронологии (Period):** В SQL-запросе Postgres жестко зашита валидация времени: `updated_at = CASE WHEN EXCLUDED.updated_at > stock_tables.updated_at THEN EXCLUDED.updated_at ELSE stock_tables.updated_at END`. Это гарантирует, что старые данные из 1С никогда не перезапишут более свежий остаток в базе при нарушении порядка сообщений в очереди.

## Запуск проекта

### 1. Настройка окружения
Создайте файл `.env` в корне проекта (конфигурация подтянется автоматически через `cleanenv`):
```env
APP_ENV=production

BATCH_SIZE=50000
BATCH_TIMEOUT=500ms

CLICKHOUSE_HOST=localhost
CLICKHOUSE_PORT=9000
CLICKHOUSE_USER=default
CLICKHOUSE_PASSWORD=
CLICKHOUSE_DB=default
CLICKHOUSE_TIMEOUT=30s

POSTGRES_HOST=localhost
POSTGRES_PORT=5432
POSTGRES_USER=postgres
POSTGRES_PASSWORD=postgres
POSTGRES_DB=marketplace
POSTGRES_TIMEOUT=5s

RABBITMQ_HOST=localhost
RABBITMQ_PORT=5672
RABBITMQ_USER=guest
RABBITMQ_PASSWORD=guest
RABBITMQ_VHOST=/
```

### 2. Запуск приложения
```bash
go run cmd/broker/main.go
```

### 3. Запуск бенчмарков производительности
```bash
  go test -v -run Test_Usecase_RealDatabase_Throughput ./internal/usecase
```

##  Вектор развития (Переход к CQRS микросервисам)
Данный проект представляет собой законченный высокопроизводительный **Write-сервис** (монолитный MVP с логикой CQRS). 

Следующим этапом развития Enterprise-архитектуры является его физическое разделение на микросервисы:
1. Выделение текущего кода в изолированный контейнер записи.
2. Создание второго независимого Go-приложения (**Read-сервиса**), которое будет заниматься исключительно быстрым чтением и отдачей отчетов оборачиваемости из ClickHouse/Postgres, полностью разгружая транзакционный пайплайн.
